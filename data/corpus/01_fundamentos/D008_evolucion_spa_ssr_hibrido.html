Evolución desde páginas multipágina hasta SPA, SSR e hidratación

Dónde se construye la interfaz de una aplicación web

A lo largo de la introducción a la evolución de la World Wide Web, una de las preguntas arquitectónicas más recurrentes ha sido dónde debe ensamblarse el HTML que ve el usuario: en el servidor antes de enviarlo por la red, o en el navegador mediante JavaScript. Tras el impacto de la web móvil y la transición al diseño adaptativo, esta discusión se volvió crítica para equilibrar fluidez interactiva y tiempo de carga inicial.

Este documento traza la evolución conceptual de estos modelos sin enseñar la API interna de React, Vue o Angular.

MPA: el modelo multipágina clásico en servidor

En una Multi-Page Application (MPA) tradicional, cada navegación solicita una ruta distinta al servidor. El backend consulta la base de datos, rellena una plantilla HTML y devuelve el documento completo. Su ventaja principal es la simplicidad operativa y la entrega inmediata de contenido indexable por buscadores, aunque cada cambio de vista reinicia el contexto de la página.

El auge de las Single Page Applications (SPA)

Con el crecimiento de aplicaciones complejas en la década de 2010 surgieron las Single Page Applications (SPA). En este modelo, el servidor entrega un archivo HTML casi vacío acompañado de un paquete JavaScript. El navegador descarga el código, ejecuta la aplicación, consulta APIs JSON y dibuja dinámicamente toda la interfaz modificando el DOM, interceptando enlaces mediante History API para navegar sin recargas.

Las SPA ofrecieron transiciones instantáneas entre vistas, pero introdujeron dos inconvenientes: una pantalla en blanco inicial mientras se descargaba y ejecutaba JavaScript pesado, y dificultades para rastreadores web que no ejecutaban scripts.

SSR e hidratación: combinando servidor y cliente

Para recuperar la velocidad de primer pintado y el posicionamiento SEO sin perder interactividad rica, la industria adoptó el Server-Side Rendering (SSR) moderno. El servidor ejecuta los componentes de la interfaz para generar el HTML inicial con datos reales y lo envía al navegador, permitiendo que el usuario vea el contenido de inmediato.

Posteriormente ocurre la hidratación: el navegador descarga el JavaScript asociado y adjunta los manejadores de eventos sobre el DOM ya existente, convirtiendo la página estática en una aplicación interactiva. Ejemplos concretos de este mecanismo incluyen el renderizado en servidor e hidratación no destructiva en Angular.

La evaluación sistemática de estos enfoques se amplía en la comparativa de estrategias de renderizado CSR, SSR, SSG e ISR y en técnicas más recientes como la hidratación progresiva, selectiva y arquitectura de islas. Todo este ecosistema evoluciona apoyado en especificaciones mantenidas por los organismos de estandarización W3C, WHATWG, IETF y TC39.

Criterios prácticos para elegir modelo de renderizado

Ningún modelo es superior en todos los escenarios; la elección depende del tipo de aplicación:

  • MPA o generación estática: Ideal para documentación, blogs y sitios editoriales donde el contenido cambia con poca frecuencia y la indexación es prioritaria.
  • SPA pura (CSR): Adecuada para paneles administrativos internos o herramientas privadas tras inicio de sesión, donde el SEO no importa y prima la interactividad continua.
  • SSR e hidratación híbrida: Recomendable para comercios electrónicos, portales públicos y aplicaciones que exigen tanto carga inicial rápida como transiciones fluidas en cliente.

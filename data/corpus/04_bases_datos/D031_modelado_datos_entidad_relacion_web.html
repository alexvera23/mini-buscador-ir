Modelado de datos para aplicaciones web: del modelo conceptual al esquema físico

Fases del diseño de bases de datos, identificación de entidades y cardinalidades, formas normales y traducción a tablas, restricciones e índices.

Las tres etapas del modelado de datos

Diseñar una base de datos robusta para una aplicación web sobre los principios de las bases de datos relacionales exige planificar la estructura antes de escribir código de servidor. Un esquema mal diseñado provoca duplicación de información, anomalías al actualizar registros y consultas cada vez más lentas. El proceso metodológico se divide en tres niveles progresivos:

  1. Modelo conceptual (Entidad-Relación): Identifica los sustantivos clave del dominio de negocio (Usuario, Curso, Inscripción), sus propiedades esenciales y cómo se vinculan entre sí, sin preocuparse aún por tipos de datos o detalles técnicos de un motor específico.
  2. Modelo lógico: Traduce las entidades en relaciones normalizadas, define claves primarias y foráneas, resuelve relaciones muchos a muchos y establece reglas de nulabilidad y unicidad.
  3. Modelo físico: Adapta el diseño lógico al motor concreto seleccionado (PostgreSQL, MySQL), eligiendo tipos de datos precisos (VARCHAR, NUMERIC(10,2) para moneda, TIMESTAMPTZ), índices sobre claves foráneas y columnas frecuentes de búsqueda, y políticas de borrado referencial.

Cardinalidades y su traducción a tablas relacionales

La cardinalidad expresa cuántas instancias de una entidad pueden asociarse con instancias de otra:

  • Uno a uno (1:1): Cada registro de la tabla A corresponde como máximo a un registro de la tabla B (por ejemplo, usuarios y perfiles_extendidos). Se implementa colocando una clave foránea con restricción UNIQUE en la tabla dependiente.
  • Uno a muchos (1:N): Es la relación más habitual en aplicaciones web (un cliente realiza múltiples pedidos, pero cada pedido pertenece a un único cliente). Se traduce colocando la clave foránea (cliente_id) en el lado "muchos" (tabla pedidos).
  • Muchos a muchos (N:M): Ocurre cuando múltiples instancias de A se relacionan con múltiples instancias de B (un estudiante se matricula en varios cursos y cada curso tiene muchos estudiantes). El modelo relacional requiere descomponer esta relación mediante una tabla intermedia o asociativa (matriculas) que contiene claves foráneas hacia ambas tablas y puede almacenar atributos propios de la relación, como fecha_inscripcion o calificacion.
CREATE TABLE estudiantes (
  id SERIAL PRIMARY KEY,
  nombre VARCHAR(120) NOT NULL
);

CREATE TABLE cursos (
  id SERIAL PRIMARY KEY,
  titulo VARCHAR(150) NOT NULL
);

CREATE TABLE matriculas (
  estudiante_id INTEGER NOT NULL REFERENCES estudiantes(id) ON DELETE RESTRICT,
  curso_id INTEGER NOT NULL REFERENCES cursos(id) ON DELETE RESTRICT,
  fecha_inscripcion DATE NOT NULL DEFAULT CURRENT_DATE,
  PRIMARY KEY (estudiante_id, curso_id)
);

Normalización y equilibrio práctico

La normalización es el proceso de organizar columnas y tablas para eliminar redundancias y dependencias anómalas. En el desarrollo web, alcanzar la Tercera Forma Normal (3FN) constituye el estándar saludable:

  • 1FN: Cada celda contiene un único valor atómico (evitando listas separadas por comas dentro de una misma columna de texto).
  • 2FN: Todos los atributos no clave dependen de la totalidad de la clave primaria (relevante en claves compuestas).
  • 3FN: Ningún atributo no clave depende transitivamente de otro atributo no clave (por ejemplo, no guardar ciudad_cliente repetida en cada fila de pedidos, sino consultarla desde clientes).

En casos puntuales de lectura intensiva —como guardar el precio_unitario_historico dentro de una línea de factura—, se aplica una desnormalización intencional y controlada para preservar fotografías históricas inmutables ante futuros cambios de precios en el catálogo.

Integridad referencial e indexación estratégica

Al definir claves foráneas conviene especificar explícitamente el comportamiento ante eliminaciones (ON DELETE RESTRICT para impedir borrar registros con historial asociado, o ON DELETE CASCADE solo para subentidades estrictamente dependientes) y crear índices explícitos sobre las columnas de clave foránea y filtros habituales (WHERE, ORDER BY) para evitar escaneos secuenciales completos conforme crece el volumen de datos.

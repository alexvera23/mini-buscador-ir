Webhooks: notificaciones basadas en eventos entre sistemas

Patrón de inversión de control mediante callbacks HTTP, verificación criptográfica con firmas HMAC, diseño idempotente y estrategias de reintento exponencial.

Inversión del flujo: de consultar (Pull) a ser notificado (Push)

Cuando nuestro servidor backend integra servicios externos —como pasarelas de pago, proveedores de envío, repositorios Git o plataformas de mensajería—, muchos eventos importantes ocurren de manera asíncrona fuera de nuestro control (por ejemplo, la confirmación bancaria de un cargo o un push en un repositorio). Consultar repetidamente la API del proveedor cada pocos segundos para detectar cambios resulta ineficiente y consume cuotas de peticiones.

Un Webhook invierte esta relación: nuestro sistema registra previamente una URL pública de recepción (callback endpoint) ante el proveedor externo y, cada vez que ocurre un evento suscrito, el proveedor dispara automáticamente una petición POST sobre el protocolo HTTP con una carga útil JSON describiendo lo sucedido.

Seguridad y verificación criptográfica con firmas HMAC

Dado que el endpoint receptor de un webhook debe estar expuesto públicamente en Internet para que el proveedor externo lo alcance, cualquier atacante que descubra esa URL podría intentar enviar peticiones falsificadas simulando que un pago fue aprobado. Nunca debe confiarse en el origen únicamente por dirección IP ni procesar el cuerpo sin autenticarlo.

El estándar de seguridad en webhooks consiste en verificar una firma criptográfica HMAC (generalmente HMAC-SHA256):

  1. Durante la configuración inicial, ambos sistemas comparten un secreto de firma almacenado de forma segura.
  2. Al enviar el evento, el emisor calcula el resumen HMAC del cuerpo crudo de la petición (a menudo combinado con una marca de tiempo para prevenir ataques de repetición) y lo incluye en una cabecera HTTP (como X-Hub-Signature-256).
  3. El servidor receptor recalcula localmente el HMAC sobre los bytes crudos recibidos y compara ambas firmas utilizando una función de comparación en tiempo constante (como crypto.timingSafeEqual) para evitar ataques de temporización.
import crypto from 'node:crypto';

function verificarFirmaWebhook(cuerpoCrudo, cabeceraFirma, secreto) {
  const esperado = 'sha256=' + crypto
    .createHmac('sha256', secreto)
    .update(cuerpoCrudo)
    .digest('hex');

  const bufRecibido = Buffer.from(cabeceraFirma || '', 'utf8');
  const bufEsperado = Buffer.from(esperado, 'utf8');

  return bufRecibido.length === bufEsperado.length &&
    crypto.timingSafeEqual(bufRecibido, bufEsperado);
}

Fiabilidad: respuesta rápida, reintentos e idempotencia

Los proveedores de webhooks suelen imponer tiempos límite estrictos (entre 3 y 10 segundos) para recibir una confirmación HTTP 2xx. Si el receptor tarda demasiado o devuelve un código 5xx, el emisor asume que la entrega falló y programa reintentos automáticos con retroceso exponencial (exponential backoff) durante horas o días.

Para operar webhooks de forma resiliente en producción se aplican dos reglas arquitectónicas esenciales:

  • Desacoplar recepción y procesamiento: El controlador HTTP debe verificar la firma, persistir el evento crudo en una cola de trabajos o tabla de eventos pendientes y responder inmediatamente 200 OK o 202 Accepted en pocos milisegundos, delegando la lógica pesada a trabajadores en segundo plano.
  • Garantizar idempotencia mediante identificador de evento: Debido a los reintentos de red, un mismo evento puede entregarse más de una vez. El receptor debe registrar el identificador único del evento (event_id) en su base de datos con una restricción de unicidad para ignorar de forma segura entregas duplicadas sin acreditar dos veces el mismo pago ni enviar correos repetidos.

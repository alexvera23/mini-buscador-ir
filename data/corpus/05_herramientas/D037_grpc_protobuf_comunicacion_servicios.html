gRPC y Protocol Buffers: comunicación binaria de alto rendimiento entre servicios

Paradigma de llamada a procedimiento remoto sobre HTTP/2, contratos estrictos en Protocol Buffers, modos de streaming y casos de uso en comunicación interna entre servicios.

El paradigma RPC moderno y el rol de gRPC

Mientras que REST modela operaciones CRUD alrededor de recursos y GraphQL prioriza consultas flexibles desde clientes visuales, gRPC (gRPC Remote Procedure Calls, creado por Google y hospedado en la Cloud Native Computing Foundation) retoma el paradigma de llamada a procedimiento remoto: permite que un servicio cliente invoque directamente métodos definidos en un servicio remoto como si fueran funciones locales.

gRPC está diseñado específicamente para minimizar la latencia, reducir el consumo de ancho de banda y garantizar contratos estrictos entre múltiples lenguajes de programación en arquitecturas internas distribuídas.

Contratos estrictos con Protocol Buffers (Protobuf)

Por defecto, gRPC utiliza Protocol Buffers (Protobuf) tanto como lenguaje de definición de interfaz (IDL) como formato de serialización binaria. El desarrollador define los mensajes y servicios en un archivo .proto neutro respecto al lenguaje, identificando cada campo con una etiqueta numérica única que permite evolucionar esquemas manteniendo compatibilidad hacia atrás y hacia adelante:

syntax = "proto3";

package inventario.v1;

service ServicioInventario {
  rpc ConsultarStock (SolicitudStock) returns (RespuestaStock);
}

message SolicitudStock {
  string sku = 1;
  int32 almacen_id = 2;
}

message RespuestaStock {
  string sku = 1;
  int32 unidades_disponibles = 2;
  bool reabastecimiento_pendiente = 3;
}

A partir de este archivo, el compilador protoc genera automáticamente clases de datos tipadas, clientes (stubs) y esqueletos de servidor en Go, Java, Python, Node.js, C#, Rust o C++. Al serializar los mensajes en un formato binario compacto en lugar de texto JSON repetitivo, los paquetes ocupan una fracción del tamaño y se analizan órdenes de magnitud más rápido en CPU.

Transporte sobre HTTP/2 y patrones de comunicación

gRPC se apoya nativamente sobre HTTP/2 (evolución descrita en protocolo HTTP a fondo), aprovechando la multiplexación de flujos binarios sobre una única conexión TCP persistente, propagación de tiempos límite (deadlines) y cancelación propagada entre llamadas encadenadas. Además, soporta cuatro patrones de comunicación:

  • RPC Unario (Unary): El cliente envía una única petición y recibe una única respuesta, equivalente a una llamada funcional tradicional.
  • Streaming del servidor (Server Streaming): El cliente envía una petición y recibe un flujo continuo de mensajes desde el servidor hasta que este cierra el canal (ideal para cotizaciones o exportación progresiva).
  • Streaming del cliente (Client Streaming): El cliente envía una secuencia de mensajes hacia el servidor y espera una única respuesta consolidada al finalizar (útil para carga fragmentada o ingestión de telemetría).
  • Streaming bidireccional (Bidirectional Streaming): Ambos extremos transmiten flujos independientes de mensajes simultáneamente sobre la misma conexión HTTP/2.

¿Cuándo preferir gRPC frente a REST?

gRPC brilla en la comunicación interna entre microservicios políglotas (tráfico este-oeste), sistemas de IoT con ancho de banda restringido y tuberías de procesamiento de baja latencia. Sin embargo, para APIs públicas abiertas a terceros o consumo directo desde navegadores web —donde el soporte nativo de HTTP/2 sin proxies intermediarios como gRPC-Web es limitado y la legibilidad directa del texto JSON facilita la depuración—, REST y OpenAPI continúan siendo la opción más accesible.

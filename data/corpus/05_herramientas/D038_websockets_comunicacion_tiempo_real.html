WebSockets y comunicación bidireccional en tiempo real

Negociación HTTP Upgrade, canal full-duplex persistente sobre TCP, comparación técnica con Polling y Server-Sent Events (SSE), y estrategias de escalado horizontal.

Limitaciones del modelo clásico petición-respuesta

En el modelo estándar del protocolo HTTP, la comunicación siempre la inicia el cliente: el servidor no puede enviar datos espontáneamente hacia el navegador sin que exista una solicitud previa pendiente. Cuando una aplicación requiere actualizaciones instantáneas —como chats colaborativos, tableros financieros en vivo, edición compartida o notificaciones críticas—, forzar HTTP clásico genera latencia o sobrecarga innecesaria.

El protocolo WebSocket y el Handshake HTTP Upgrade

Estandarizado en el RFC 6455, el protocolo WebSocket (esquemas ws:// y wss:// sobre TLS) establece un canal de comunicación bidireccional simultáneo (full-duplex) y persistente sobre una única conexión TCP.

Para atravesar sin fricciones firewalls y proxies web existentes, toda conexión WebSocket comienza como una petición HTTP/1.1 convencional que solicita cambiar de protocolo mediante las cabeceras Upgrade y Connection:

GET /canal-eventos HTTP/1.1
Host: api.ejemplo.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Una vez recibida la respuesta 101 Switching Protocols, la conexión abandona el formato HTTP y ambos extremos intercambian tramas ligeras (frames) binarias o UTF-8 con apenas unos pocos bytes de sobrecarga, eliminando el envío repetitivo de cabeceras HTTP en cada mensaje.

Alternativas de tiempo real: Polling, Long Polling y SSE

Antes de adoptar WebSockets conviene evaluar si el flujo de datos realmente requiere bidireccionalidad constante o si basta con alternativas más simples sobre HTTP:

  • Short Polling: El cliente consulta periódicamente mediante GET cada ciertos segundos. Es trivial de implementar, pero desperdicia recursos cuando no hay novedades e introduce latencia proporcional al intervalo de sondeo.
  • Long Polling: El servidor retiene la petición HTTP abierta hasta que ocurre un evento nuevo o expira un tiempo límite, momento en que responde y el cliente abre inmediatamente otra solicitud.
  • Server-Sent Events (SSE): Estándar nativo de HTML5 (EventSource) sobre HTTP convencional que establece un flujo unidireccional continuo del servidor hacia el cliente (Content-Type: text/event-stream). Incluye reconexión automática nativa, soporta HTTP/2 y resulta ideal para paneles de monitoreo, feeds de noticias o transmisión progresiva de respuestas de modelos de lenguaje donde el cliente apenas envía mensajes.
  • WebSockets: Indispensable cuando tanto el cliente como el servidor emiten mensajes frecuentes de baja latencia en ambas direcciones simultáneamente.

Gestión de conexiones persistentes y escalado horizontal

A diferencia de las APIs REST sin estado, un servidor WebSocket mantiene conexiones activas en memoria durante minutos u horas. Esto exige implementar mecanismos periódicos de latido (Ping/Pong heartbeats) para detectar desconexiones silenciosas en redes móviles y liberar recursos.

Asimismo, al escalar horizontalmente detrás de un balanceador de carga con múltiples instancias de servidor, un usuario conectado a la instancia A no recibirá directamente un mensaje publicado en la instancia B. Para coordinar múltiples nodos se intercala un bus de mensajería distribuido mediante patrones Pub/Sub (como Redis Pub/Sub o NATS) que difunde cada evento hacia todas las instancias suscritas.

GraphQL: esquemas tipados, consultas declarativas y mutaciones

Lenguaje de consulta para APIs basado en esquemas fuertemente tipados, resolución de over-fetching y under-fetching, operaciones Query, Mutation y Subscription, y gestión de complejidad.

¿Por qué surgió GraphQL frente a REST tradicional?

Desarrollado internamente por Facebook en 2012 y liberado como especificación abierta en 2015, GraphQL es un lenguaje de consulta y un entorno de ejecución para APIs que replantea el intercambio de datos respecto a la arquitectura REST tradicional y el uso múltiple de endpoints sobre HTTP.

En aplicaciones móviles y clientes frontend complejos con múltiples vistas heterogéneas, consumir endpoints REST fijos suele provocar dos ineficiencias recurrentes:

  • Over-fetching (sobrecarga de datos): El endpoint devuelve un objeto JSON completo con treinta atributos cuando la vista móvil únicamente necesitaba el nombre y la miniatura del usuario, desperdiciando ancho de banda y tiempo de deserialización.
  • Under-fetching (insuficiencia de datos): Un único endpoint no entrega toda la información relacionada necesaria, obligando al cliente a realizar múltiples peticiones secuenciales en cascada (por ejemplo, obtener el usuario, luego sus proyectos y después los colaboradores de cada proyecto).

GraphQL resuelve ambos problemas exponiendo generalmente un único punto de entrada (POST /graphql) donde el cliente describe declarativamente la forma exacta de los datos que desea recibir en una sola petición de red.

El Esquema (SDL) como contrato fuertemente tipado

Todo servidor GraphQL se articula alrededor de un esquema escrito mediante el Schema Definition Language (SDL). Este esquema actúa como la única fuente de verdad entre cliente y servidor, definiendo tipos de objeto, escalares (Int, Float, String, Boolean, ID), relaciones entre entidades y nulabilidad explícita (indicada con !):

type Autor {
  id: ID!
  nombre: String!
  libros: [Libro!]!
}

type Libro {
  id: ID!
  titulo: String!
  anioPublicacion: Int!
  autor: Autor!
}

type Query {
  libro(id: ID!): Libro
  librosPorAnio(anio: Int!): [Libro!]!
}

type Mutation {
  crearLibro(titulo: String!, anioPublicacion: Int!, autorId: ID!): Libro!
}

Queries, Mutations, Subscriptions y Resolvers

Las interacciones en GraphQL se clasifican en tres tipos raíz de operación:

  • Queries (Consultas): Operaciones de solo lectura donde el cliente selecciona los campos exactos a proyectar. La respuesta JSON replica fielmente la estructura jerárquica solicitada en la consulta.
  • Mutations (Mutaciones): Operaciones que modifican estado en el servidor (creación, actualización o borrado) y permiten seleccionar inmediatamente en la misma petición los campos actualizados del recurso resultante.
  • Subscriptions (Suscripciones): Flujos persistentes en tiempo real (habitualmente transportados sobre WebSockets) que notifican automáticamente a los clientes suscritos cuando ocurre un evento específico en el servidor.

En el backend, cada campo del esquema está respaldado por una función denominada Resolver, responsable de obtener el valor correspondiente desde una base de datos, un microservicio o una caché.

Compromisos operativos: caché, errores y consultas profundas

Adoptar GraphQL introduce desafíos arquitectónicos que deben gestionarse deliberadamente:

  • Caché HTTP estándar: Dado que casi todas las peticiones viajan como POST hacia una única URL con cuerpo variable, no es posible aprovechar directamente las cachés HTTP intermediarias basadas en URI, requiriendo cachés normalizadas en el cliente (como Apollo Client o Urql) o consultas persistidas vía GET.
  • Problema N+1 en resolvers: Ejecutar consultas individuales a base de datos dentro de resolvers anidados puede saturar el motor de persistencia si no se agrupan y cachean por lote dentro de cada petición mediante el patrón DataLoader.
  • Protección contra abuso: Un cliente malicioso podría enviar consultas profundamente anidadas (autor -> libros -> autor -> libros...). En producción es indispensable configurar límites máximos de profundidad (query depth limiting), análisis de costo de complejidad y desactivar la introspección pública si la API es privada.

Diseño de APIs web: contratos, recursos y comunicación cliente-servidor

Modelado de recursos sobre HTTP, diseño de contratos explícitos y evolutivos, semántica de métodos y criterios para elegir entre REST, GraphQL y RPC.

La API como contrato entre productores y consumidores

En la ingeniería de servidores backend, una API (Application Programming Interface) web define la frontera formal mediante la cual clientes —aplicaciones web, móviles o servicios de terceros— invocan capacidades del sistema sin conocer su implementación interna.

Diseñar una buena API consiste ante todo en diseñar un contrato explícito, predecible y estable. Cuando los equipos acuerdan de antemano las rutas, estructuras de datos, reglas de validación y formatos de error antes de escribir código, el desarrollo frontend y backend puede avanzar en paralelo sin bloqueos ni malentendidos.

Principios de diseño orientado a recursos (REST sobre HTTP)

El estilo arquitectónico predominante en la web pública y empresarial es REST (Representational State Transfer), que aprovecha directamente la semántica nativa del protocolo HTTP en lugar de reinventar mecanismos de transporte propios:

  • Identificación mediante sustantivos en plural: Las URIs representan colecciones e instancias de recursos (/api/v1/ordenes, /api/v1/ordenes/482), evitando verbos de acción en la ruta como /obtenerOrdenes o /borrarOrden.
  • Semántica estándar de métodos HTTP: GET consulta representaciones sin alterar el estado del servidor (operación segura e idempotente); POST crea nuevos recursos dentro de una colección; PUT reemplaza íntegramente un recurso existente; PATCH aplica modificaciones parciales; y DELETE elimina el recurso indicado.
  • Códigos de estado significativos: El servidor comunica el resultado mediante códigos estándar: 200 OK, 201 Created (acompañado de la cabecera Location), 204 No Content, 400 Bad Request o 422 Unprocessable Entity para errores de validación, 401 Unauthorized, 403 Forbidden, 404 Not Found y 500 Internal Server Error.
  • Respuestas de error uniformes: Estandarizar una estructura JSON consistente para fallos (por ejemplo, siguiendo el estándar RFC 9457 Problem Details) permite que los clientes manejen errores de forma centralizada.
// Ejemplo de respuesta de error estructurada y predecible (HTTP 422)
{
  "type": "https://api.ejemplo.com/errores/validacion",
  "title": "Datos de entrada inválidos",
  "status": 422,
  "detail": "Uno o más campos no cumplen las reglas de negocio.",
  "errores": [
    { "campo": "cantidad", "mensaje": "Debe ser un entero mayor a cero" }
  ]
}

Paginación, filtrado y evolución sin rupturas

Exponer colecciones sin límites degrada el rendimiento de la base de datos y satura la red del cliente. Toda colección potencialmente extensa debe soportar paginación explícita —ya sea basada en desplazamiento (?page=2&limit=25) o basada en cursores opacos (?cursor=eyJpZCI6MTAwfQ==) para conjuntos dinámicos de alto volumen— junto con parámetros estandarizados de filtrado y ordenamiento (?estado=activo&sort=-fechaCreacion).

Asimismo, las APIs evolucionan con el negocio. Para evitar romper clientes existentes en producción, conviene aplicar cambios aditivos compatibles hacia atrás (añadir campos opcionales sin eliminar ni renombrar los existentes) y reservar el versionado explícito (como el prefijo /v1/ a /v2/) únicamente para cambios estructurales incompatibles.

Comparación de paradigmas: REST, GraphQL y RPC

Aunque REST cubre eficazmente la mayoría de escenarios web, existen casos donde otros estilos de comunicación ofrecen ventajas concretas:

  • REST: Ideal para APIs públicas, recursos bien definidos, aprovechamiento nativo del almacenamiento en caché HTTP (ETags, Cache-Control) y herramientas universales de depuración.
  • GraphQL: Expone un único punto de entrada donde el cliente declara exactamente qué campos y relaciones necesita mediante un esquema fuertemente tipado. Resuelve los problemas de over-fetching (recibir datos sobrantes) y under-fetching (necesitar múltiples peticiones encadenadas) en interfaces complejas con múltiples clientes, a cambio de mayor complejidad en caché y protección contra consultas profundamente anidadas.
  • RPC (como gRPC o tRPC): Orientado a invocar procedimientos remotos directamente. gRPC utiliza Protocol Buffers binarios sobre HTTP/2, ofreciendo latencia mínima y contratos estrictos ideales para comunicación interna entre microservicios; tRPC permite compartir tipos de extremo a extremo en proyectos monorepo construidos íntegramente con TypeScript.

Documentar el contrato mediante especificaciones legibles por máquinas como OpenAPI (para REST) o esquemas SDL (para GraphQL) permite generar automáticamente clientes tipados, pruebas de contrato y portales de documentación interactiva.

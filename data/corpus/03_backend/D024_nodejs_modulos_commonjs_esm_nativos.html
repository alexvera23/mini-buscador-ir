Módulos en Node.js: CommonJS frente a ES Modules y APIs estándar

Evolución del sistema de modularización en Node.js, diferencias técnicas entre CommonJS y ECMAScript Modules, resolución de rutas y biblioteca estándar integrada.

Necesidad de modularización en el servidor

Cuando Node.js nació en 2009, el estándar JavaScript carecía de un mecanismo oficial para dividir programas en múltiples archivos con ámbitos aislados. Para construir servidores backend mantenibles sobre la arquitectura de Node.js, resultó imprescindible evitar la contaminación del espacio de nombres global mediante sistemas de módulos explícitos.

CommonJS (CJS): el sistema histórico de Node.js

Node.js adoptó originalmente la especificación CommonJS, caracterizada por las funciones require() para importar dependencias y el objeto module.exports (o su alias exports) para exponer funcionalidad pública.

// calculadora.cjs
function sumar(a, b) {
  return a + b;
}

module.exports = { sumar };

// app.cjs
const { sumar } = require('./calculadora.cjs');
console.log(sumar(4, 6));

En CommonJS, la carga de módulos es síncrona y dinámica: require() lee el archivo desde el disco, lo envuelve en una función aislada con variables locales (__dirname, __filename, module, exports), lo evalúa en tiempo de ejecución y almacena el objeto exportado en una caché interna para futuras llamadas. Al ser una función ordinaria de JavaScript, permite invocarse condicionalmente dentro de bloques if.

ES Modules (ESM): el estándar oficial de JavaScript

Con la llegada de ECMAScript 2015 (ES6), JavaScript incorporó un sistema de módulos nativo basado en las palabras clave import y export. Node.js soporta plenamente ES Modules, activándose cuando el archivo posee extensión .mjs o cuando el archivo package.json más cercano declara el campo "type": "module" (permitiendo usar .js estándar).

// calculadora.js (con "type": "module" en package.json)
export function sumar(a, b) {
  return a + b;
}

// app.js
import { sumar } from './calculadora.js';
console.log(sumar(4, 6));

Las diferencias arquitectónicas clave de ESM respecto a CommonJS incluyen:

  • Análisis estático: Las sentencias import y export se resuelven antes de ejecutar el código, habilitando optimizaciones como eliminación de código muerto (tree-shaking) y detección temprana de exportaciones inexistentes.
  • Carga asíncrona y Top-Level Await: ESM permite utilizar await directamente en el nivel superior de un módulo sin necesidad de envolverlo en una función async.
  • Extensiones explícitas en rutas relativas: En Node.js ESM, las importaciones relativas requieren especificar la extensión completa del archivo (./utilidades.js) y sustituyen __dirname por import.meta.url.

Módulos estándar integrados y prefijo node:

Node.js incluye una extensa biblioteca estándar que cubre operaciones habituales de servidor sin instalar dependencias externas. La buena práctica moderna consiste en importar estos módulos utilizando el prefijo explícito node: (por ejemplo, import fs from 'node:fs/promises'), lo que acelera la resolución y evita colisiones con paquetes de terceros del mismo nombre:

  • node:fs y node:fs/promises: Lectura, escritura, transmisión mediante flujos (streams) y manipulación de archivos y directorios.
  • node:path: Construcción y normalización segura de rutas de archivos independientes del separador del sistema operativo (path.join, path.resolve).
  • node:crypto: Generación de identificadores aleatorios seguros (randomUUID), funciones resumen criptográficas (SHA-256), firmas HMAC y derivación de claves.
  • node:http y node:https: Creación directa de servidores y clientes HTTP de bajo nivel, sobre los cuales se construyen frameworks como Express y Fastify.
